## 正文

### 一、为什么又造一个轮子

起因很简单：我想验证一个直觉——格斗游戏的门槛，可能没有想象中那么高。

不需要 3D 引擎，不需要动作捕捉，不需要几百兆素材。一个 2D 格斗游戏的核心，是**帧**：每一招在第几帧起手、第几帧判定、第几帧收招，打中之后对手僵直多少帧、被推开多远。这些数字对了，手感就对了。

于是我给自己定了一个约束：**零依赖**。不用游戏引擎，不用构建工具，不用一张图片。所有角色、场景、特效，都用代码画出来。

最后的成品叫 NEON RUMBLE，大约 2000 行，能在浏览器里直接打。

### 二、它现在能玩什么

- 三局两胜、99 秒读秒，KO 和时间到都有判定
- 轻拳、重拳、踢、下段、跳跃攻击、波动、100 气超杀
- 起手 / 判定 / 收招帧，命中硬直、防御硬直、击倒、起身无敌
- 下段必须蹲防，跳跃攻击是 overhead，波动被挡也有削血
- 连段伤害递减，避免一套带走
- CPU 会接近、立回、防空、发波，也会防御

键盘操作：`WASD` 移动，`J` 轻拳、`K` 重拳、`L` 踢；`↓↘→` + 攻击是波动，`↓↘→↓↘→` + 重拳是超杀。

### 三、拆开看：七个文件

| 文件 | 职责 |
| --- | --- |
| `config.js` | 帧数据、角色数值、按键映射 |
| `fighter.js` | 单个角色的状态机、移动、判定框 |
| `engine.js` | 命中判定、飞行道具、回合流程、相机 |
| `ai.js` | CPU 对手 |
| `render.js` | 场景、角色、特效、HUD |
| `input.js` | 键盘与指令识别 |
| `main.js` | 主循环、标题界面、暂停、音效 |

关键的分层是：**战斗模拟不碰 DOM**。`fighter`、`engine`、`ai` 只处理数字和状态，渲染层单独读状态画图。这样同一套逻辑既能在浏览器里跑，也能在 Node 里跑测试。

### 四、三个真正花时间的点

**1. 相机与世界坐标**

第一版角色只出现在屏幕左半边——因为我把世界坐标直接画到了画布上，忘了减去相机偏移。修复只需要一行 `translate(-cameraX)`，但定位这个 bug 花的时间比写相机跟随还久。

**2. 防御判定不是“按住后退”**

下段必须蹲防，跳跃攻击必须站防，空中不能防。判断函数要同时看：是否按住反方向、是否下蹲、是否在空中、当前状态是否允许防御。写错一个条件，就会出现“明明防了却被打中”。

**3. 连段递减**

如果没有伤害递减，一套连招就能打掉七成血。现在每多一段，伤害乘一个衰减系数，最低到 40%。这让连段有价值，但不至于一套定胜负。

### 五、怎么证明它没坏

战斗逻辑不依赖浏览器，所以测试可以直接在 Node 里跑：

- 两个 AI 打满一整场，检查位置、血量、气条不越界
- 重拳命中掉血
- 防御普通技零削血
- 波动能生成、能飞行、能命中
- 致命伤进入 KO 并记分
- 超杀消耗 100 气
- 新回合重置血量但保留气条

7 组断言，GitHub Actions 每次 push 都跑。上面这些不是“感觉没问题”，是每次提交都会被验证。

### 七、最后

这个项目让我确认了一件事：**“手感”不是玄学，是可拆解的参数**。起手快 2 帧、硬直多 3 帧，玩家的体感就完全不同。
